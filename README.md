# سامانه مدیریت تولید و خدمات پس از فروش تجهیزات پزشکی

**MD-MES** — سامانه یکپارچهٔ فارسی (RTL) برای مدیریت کامل چرخهٔ «دستور تولید ← تولید ← کنترل کیفیت ← آزادسازی ← تحویل ← خدمات پس از فروش» با رهگیری کامل (Traceability)، کنترل دسترسی نقش‌محور (RBAC) و ردیابی ممیزی (Audit Trail).

- **نسخه:** ۱٫۰٫۰
- **زبان رابط کاربری:** فارسی (RTL کامل، فونت وزیرمتن، اعداد فارسی، تاریخ جلالی)
- **پشتهٔ فناوری:** Next.js 16 (App Router) + React 19 + TypeScript 5 + Prisma 6 / SQLite + Tailwind CSS 4 + shadcn/ui + dnd‑kit + Recharts + Zod

> 🪟 **کاربر ویندوز؟** راهنمای تصویری گام‌به‌گام مخصوص ویندوز (PowerShell/CMD، رفع اشکال‌های رایج ویندوز مثل ExecutionPolicy و پورت اشغال) در فایل **`WINDOWS-SETUP.md`** همین بسته آماده شده است.

## ۱. معرفی

این سامانه برای تولیدکنندگان تجهیزات پزشکی طراحی شده است و تمام فرایندهای موردنیاز یک نظام مدیریت کیفیت (QMS) را در قالب یک نرم‌افزار یکپارچه پوشش می‌دهد: از صدور درخواست تولید (بر اساس دستور مدیریت، صورت‌جلسه یا سفارش مشتری) تا تولید مرحله‌به‌مرحله، سه سطح کنترل کیفیت (ورودی، حین تولید، نهایی)، آزادسازی محصول، انبارش، ارسال، گارانتی، تیکت‌های خدمات، تعمیرات، شکایات مشتریان و گزارش‌های مدیریتی.

اصول طراحی سامانه عبارت‌اند از:

1. **سلامت داده‌ها:** هیچ رکورد حذف فیزیکی نمی‌شود؛ همهٔ موجودیت‌ها Archive/Deactivate می‌شوند و دفتر گردش کالا (Stock Movement Ledger) از نوع «فقط‌الحاقی» (Append‑Only) است.
2. **رهگیری کامل:** هر دستگاه با شمارهٔ سریال یکتا، از «شمارهٔ لات قطعه» تا «نصب روی کدام دستگاه» و برعکس، دوطرفه رهگیری می‌شود؛ نسخهٔ BOM و نسخهٔ فرمور هر دستگاه در پرونده ثبت می‌شود.
3. **کنترل دسترسی سخت:** ماتریس ۹ نقش × حدود ۵۰ مجوز، به‌صورت سه‌لایه (رابط کاربری، سرور API و قواعد پایگاه‌داده) اعمال می‌شود.
4. **گردش‌کار کنترل‌شده:** گذار وضعیت‌ها فقط با مجوز و گاردهای سمت سرور انجام می‌شود (مثلاً «آزادسازی محصول» فقط توسط QC مجاز).
5. **ردیابی ممیزی:** هر تغییر با کاربر، نقش، مقادیر قبلی/جدید، زمان و موجودیت ثبت می‌شود.

> ⚠️ **ملاحظهٔ رگولاتوری:** این سامانه فرایندهای موردنیاز QMS را پشتیبانی می‌کند، اما تا پیش از اعتبارسنجی رسمی توسط سازمان شما، نباید ادعای انطباق با ISO 13485 مطرح شود.

## ۲. قابلیت‌های کلیدی

| حوزه | قابلیت‌ها |
|------|-----------|
| **داشبورد مدیریتی** | KPIهای تولید/کیفیت/خدمات، نمودارهای Recharts، دسترسی سریع به ماژول‌ها، اعلان‌های نقش‌محور |
| **درخواست تولید** | سه مبدأ: «دستور مدیریت / صورت‌جلسه / سفارش مشتری» (+ داخلی)، ثبت «تعداد، کد دستگاه، نام دستگاه»، اولویت و مهلت |
| **برد کانبان (کاریز فروش‌گونه)** | نمای کشیدنی (Drag & Drop با dnd‑kit) — هر کارت سفارش را با درگ به مرحلهٔ بعد منتقل کنید؛ سرور گذار را با گارد اعتبارسنجی می‌کند |
| **برنامه‌ریزی تولید** | زنجیرهٔ ۱۰ مرحله‌ای سفارش با Stepper گرافیکی، مراحل تولید (Process Steps)، ضبط رویداد هر مرحله توسط اپراتور |
| **انبار دوسویه** | ورود/خروج دستی (با دلیل اجباری) **+ مصرف خودکار BOM**: با ثبت «۱۰ ست از BOM مصرف شد»، مواد به‌صورت اتمیک و FIFO کسر می‌شود؛ پیش‌نمایش زندهٔ «موجود/کسری» قبل از ثبت |
| **دفتر گردش کالا** | دفتر تغییرناپذیر برای همهٔ تغییرات موجودی (ورود، خروج، تعدیل، مصرف تولید، رد IQC) با موجودی قبل/بعد |
| **کنترل کیفیت ورودی (IQC)** | مواد پس از ورود به «ناحیهٔ مال‌رسید» بازرسی می‌شوند؛ فقط پس از تأیید QC به‌صورت رسمی وارد انبار می‌شوند؛ رد لات → NCR + خروج از موجودی |
| **کنترل کیفیت حین/پایان تولید** | قالب‌های تست، ثبت نتایج توسط اپراتور، تأیید QC، Retest زنجیره‌ای پس از Rework، بلاک تجهیزات کالیبره‌شدهٔ منقضی |
| **عدم انطباق (NCR) و Rework** | گردش‌کار کامل NCR: باز ← Rework ← Retest ← رفع ← بستن، با ثبت اقدام اصلاحی/پیشگیرانه (CAPA) |
| **آزادسازی محصول (Release)** | فقط کاربر مجاز QC؛ گاردهای «تست نهایی انجام‌شده + QC پاس برای همهٔ دستگاه‌ها» |
| **انبار محصول و ارسال** | پس از تکمیل: ورود به انبار محصول یا ارسال مستقیم؛ سپس «خروج و ارسال» ← «بستن پروژه» |
| **پروندهٔ دیجیتال دستگاه** | شناسنامهٔ کامل هر دستگاه: سریال، BOM نسخهٔ لحظهٔ تولید، قطعات مصرفی (لات)، تست‌ها، فرمور، تحویل، گارانتی |
| **خدمات پس از فروش** | تیکت ۹ وضعیتی، تعمیر با مصرف قطعه (دوطرفه با لات)، محاسبهٔ خودکار گارانتی، تمدید دستی با مجوز، شکایت ۶ وضعیتی با CAPA و بازبینی رگولاتوری |
| **مدیریت مستندات** | بارگذاری/دریافت مستندات فنی با کنترل دسترسی |
| **ورود/خروج اکسل** | جادوگر هوشمند ورود داده: آپلود فایل ← تشخیص خودکار نوع هر شیت (موجودی انبار / BOM / سوابق تولید / تأمین‌کننده) ← انتخاب و اجرا با گزارش شفاف؛ تطبیق هوشمند نام اقلام (100nf در برابر 1000uf تشخیص داده می‌شود)؛ خروجی Excel استایل‌دار RTL برای قطعات، دستگاه‌ها، مشتریان، BOM، دفتر گردش، **گزارش ممیزی (Audit Trail)** و پشتیبان کامل |
| **گزارش‌ها** | تولید، کیفیت، خدمات، رتبه‌بندی‌ها، روند شکایت‌ها و تعمیرها |
| **مدیریت سامانه** | ردیابی ممیزی (Audit Log)، مدیریت کاربران، پشتیبان‌گیری، نمای مستندات معماری |
| **امنیت** | رمز عبور scrypt + salt، نشست DB با توکن هش‌شده، کوکی httpOnly، محدودیت نرخ ورود، اعتبارسنجی Zod در همهٔ APIها |

## ۴. نصب و راه‌اندازی گام‌به‌گام

> در همهٔ دستورها، اگر از **Bun** استفاده می‌کنید، `npm` را با `bun` و `npx` را با `bunx` جایگزین کنید.

### گام ۱ — استخراج و ورود به پوشهٔ پروژه

پیش از هر کاری، محتوای این بسته را استخراج کنید و در ترمینال به پوشهٔ پروژه بروید:

```bash
cd medical-device-mes
```

### گام ۲ — نصب بسته‌ها

```bash
npm install
```

### گام ۳ — تنظیم فایل محیط (.env)

فایل `.env.example` را به `.env` کپی کنید و مسیر پایگاه‌داده را تنظیم کنید:

```bash
cp .env.example .env        # لینوکس/مک/Git Bash
```

در ویندوز (PowerShell):

```powershell
Copy-Item .env.example .env
```

سپس فایل `.env` را باز کنید و `DATABASE_URL` را تنظیم کنید. **مقدار پیش‌فرض بدون تغییر کار می‌کند:**

```ini
DATABASE_URL="file:../db/custom.db"
```

> ⚠️ **دقت:** مسیرهای نسبی در Prisma نسبت به پوشهٔ `prisma` (محل فایل schema) تفسیر می‌شوند؛ به همین دلیل شکل صحیح نسبی `file:../db/custom.db` است. در صورت تردید از مسیر مطلق استفاده کنید — در ویندوز به‌جای `\` از `/` بنویسید:

```ini
DATABASE_URL="file:C:/medical-device-mes/db/custom.db"   # ویندوز
DATABASE_URL="file:/home/USER/medical-device-mes/db/custom.db"   # لینوکس/مک
```

### گام ۴ — تولید کلاینت Prisma

```bash
npx prisma generate
```

### گام ۵ — پایگاه‌داده

**الف) استفاده از پایگاه‌دادهٔ نمونهٔ همراه بسته (پیشنهادی برای ارزیابی سریع):**

فایل `db/custom.db` همراه بسته، شامل داده‌های نمایشی (کاربران، محصولات، سفارش‌ها، دستگاه‌ها، تیکت‌ها و…) است؛ نیازی به کار اضافه نیست.

**ب) ساخت پایگاه‌دادهٔ تمیز از صفر:**

```bash
npx prisma db push
npm run db:seed      # معادل: npx tsx scripts/seed.ts
```

> **ابزار tsx** از قبل در `devDependencies` بسته قرار دارد و همراه `npm install` نصب می‌شود؛ نیازی به نصب جداگانه نیست.

### گام ۶ — اجرا

```bash
npm run dev
```

سپس در مرورگر: **http://localhost:3000**

اگر پورت ۳۰۰۰ اشغال است:

```bash
npx next dev -p 3001
```

## ۷. نمای کلی معماری

### ۷.۱. مدل داده (۳۶ موجودیت)

اسکیمای Prisma به‌صورت رابطه‌ای و نرمال‌شده طراحی شده است؛ برای هر رکورد: کلید اصلی (cuid)، کلیدهای خارجی با یکپارچگی ارجاعی، قیدهای یکتا (Unique)، ایندکس‌ها و مهرهای زمانی (CreatedAt/UpdatedAt) در نظر گرفته شده است. ماژول‌های اصلی موجودیت‌ها:

- **هویت و دسترسی:** User، Session (توکن هش‌شده)، AuditLog، Notification، NotificationRead
- **محصول و ساختار:** Product، ProductRevision (نسخهٔ کنترل‌شده)، Bom، BomItem (نسخهٔ BOM هرگز بازنویسی نمی‌شود؛ سفارش‌ها به نسخهٔ لحظهٔ تولید قفل می‌شوند)
- **مواد و انبار:** Component، ComponentLot (لات با وضعیت IQC)، StockMovement (دفتر گردش فقط‌الحاقی)، Supplier، IncomingInspection
- **تولید:** ProcessStepTemplate، ProductionOrder (با مبدأ درخواست)، OrderStep، StepRecord، OrderMaterial
- **دستگاه و رهگیری:** Device (سریال یکتا)، DevicePartUsage (دوطرفهٔ لات ↔ دستگاه)، TestTemplate، TestResult، Equipment (کالیبراسیون)
- **کیفیت و انطباق:** Nonconformity، ReworkRecord، ProductRelease (آزادسازی)
- **فروش و خدمات:** Customer، ServiceTicket، TicketUpdate، Complaint، Repair، RepairPart، WarrantyOverride
- **مستندات:** Document

### ۷.۲. نقش‌ها و کنترل دسترسی (RBAC)

نُه نقش سامانه: **مدیر سیستم، مدیر تولید، اپراتور تولید، مسئول کنترل کیفیت، انباردار، مدیر خدمات پس از فروش، تکنسین خدمات، واحد فروش، مشاهده‌گر**.

تعریف مجوزها در `src/lib/rbac.ts` به‌صورت «تک‌منبع» نگه‌داری می‌شود و هم در سرور و هم در کلاینت از همان استفاده می‌شود تا ناهمخوانی پیش نیاید. الگوی نام‌گذاری مجوزها «ماژول + عمل» است؛ نمونه‌ها:

| ماژول | نمونهٔ مجوزها |
|-------|----------------|
| تولید | `production.create` ،`production.approve` ،`production.start` ،`production.ship` ،`production.warehouse` |
| انبار | `inventory.receive` ،`inventory.move` (خروج دستی) ،`inventory.bomConsume` ،`inventory.adjust` |
| کیفیت | `qc.incoming.decide` ،`qc.test.verify` ،`qc.ncr.manage` ،`qc.release` ،`qc.equipment.manage` |
| خدمات | `service.assign` ،`service.complaint.manage` ،`service.warranty.override` ،`service.regulatory.review` |
| سامانه | `users.manage` ،`system.backup` ،`audit.view` ،`documents.upload` |

هر API پیش از اجرا، مجوز کاربر نشست‌دار را می‌سنجد و UI نیز دکمه‌های غیرمجاز را مخفی/غیرفعال می‌کند؛ اما مرجع نهایی همیشه سرور است.

## ۸. گردش‌کارها (با گارد سمت سرور)

### ۸.۱. سفارش تولید — زنجیرهٔ کامل

```
ثبت (DRAFT) → تأیید (APPROVED) → بررسی مواد (MATERIAL_CHECK) → آماده (READY)
→ در حال تولید (IN_PRODUCTION) → در انتظار QC (WAITING_QC)
→ [در صورت خرابی: REWORK ← Retest ← بازگشت به QC]
→ تکمیل (COMPLETED) → انبار محصول (IN_WAREHOUSE) یا ارسال مستقیم (SHIPPED)
→ خروج و ارسال (SHIPPED) → بستن پروژه (CLOSED)          (+ شاخهٔ CANCELLED)
```

برخی گاردهای مهم سرور:

- «تأیید»: سفارش باید BOM فعال داشته باشد (`hasBom`)
- «شروع تولید»: نبود کمبود بحرانی مواد (`noCriticalShortage`) — عبور اضطراری فقط با مجوز `production.overrideShortage`
- «ارسال به QC»: همهٔ مراحل تولید ثبت شده باشد (`allStepsDone`)
- «تکمیل»: همهٔ دستگاه‌ها QC پاس باشند (`allDevicesQcPass`)
- «انبار محصول»: همهٔ دستگاه‌ها آزادسازی شده باشند (`allDevicesReleased`)
- «ارسال»: همهٔ دستگاه‌ها تحویل‌شده باشند (`allDevicesDelivered`)

**مبدأ درخواست تولید:** `DIRECTIVE` (دستور مدیریت — شمارهٔ دستور الزامی)، `MINUTES` (صورتجلسه — شمارهٔ صورتجلسه الزامی)، `CUSTOMER_ORDER` (سفارش مشتری — انتخاب مشتری الزامی)، `INTERNAL` (داخلی). در فرم جدید، «تعداد، کد دستگاه و نام دستگاه» ثبت می‌شود.

### ۸.۲. برد کانبان (نمای کاریز فروش)

در نما «سفارش‌ها»، تب «برد کانبان» فازهای پروژه را به‌صورت ستون‌های عمودی نمایش می‌دهد. کارت هر سفارش (کد، مشتری/مبدأ، تعداد، اولویت، مهلت) با **کشیدن و رهاکردن** (dnd‑kit) بین ستون‌ها جابه‌جا می‌شود. نکات کلیدی:

- ستون‌های مجاز برای درگ بر اساس مجوز نقش شما هایلایت می‌شوند؛ گذارهای غیرمجاز در سرور رد می‌شوند.
- پس از رهاکردن کارت، درخواست گذار به سرور ارسال و در صورت موفقیت، وضعیت و اعلان‌ها به‌روزرسانی می‌شود.
- نمای فهرستی نیز برای کاربرانی که ترجیح جدول دارند در تب دیگری موجود است.

### ۸.۳. انبار — عملیات دوسویه

| عمل | شرح |
|-----|------|
| **ورود دستی (Receive)** | ثبت رسید لات جدید با تأیید IQC، شمارهٔ لات، تاریخ انقضا و تأمین‌کننده |
| **خروج دستی (Move/Out)** | با «دلیل اجباری»؛ انتخاب لات مشخص یا FIFO خودکار؛ به رزروهای سفارش‌های فعال احترام می‌گذارد |
| **مصرف خودکار BOM** | انتخاب سفارش + تعداد ست؛ پیش‌نمایش زندهٔ «موردنیاز/قابل‌استفاده/کسری»؛ ثبت اتمی: یا همهٔ اقلام کسر می‌شود یا هیچ‌کدام؛ کسر لات‌ها به ترتیب FIFO |
| **تعدیل (Adjust)** | اصلاح موجودی با ثبت دلیل در دفتر |
| **دفتر گردش کالا** | همهٔ رویدادهای فوق + رد IQC، با «کد یکتا، نوع، مقدار علامت‌دار، موجودی قبل/بعد، کاربر، دلیل» — تغییرناپذیر |

### ۸.۴. کنترل کیفیت ورودی (گیت IQC)

مواد واردشده ابتدا در وضعیت «در انتظار بازرسی» می‌مانند (در موجودی قابل‌مصرف نیستند). مسئول QC نتیجه را ثبت می‌کند: **تأیید** ← لات وارد موجودی می‌شود و رویداد دفتر ثبت می‌گردد؛ **رد** ← NCR صادر می‌شود، لات از موجودی خارج و رویداد خروج در دفتر ثبت می‌شود.

### ۸.۵. تیکت خدمات (۹ وضعیت)

```
جدید → در حال بررسی → ارجاع → عیب‌یابی → [در انتظار قطعه] → در حال تعمیر
→ تست پس از تعمیر → رفع‌شده → بسته‌شده
```

هر تعمیر می‌تواند قطعات مصرفی با لات ثبت کند (رهگیری دوسویهٔ «کدام لات روی کدام دستگاه»).

### ۸.۶. شکایت مشتری (۶ وضعیت) و NCR (۶ وضعیت)

شکایت: باز ← در حال بررسی ← ثبت CAPA ← در انتظار تأیید ← بسته/ردشده (با قیدهای علت ریشه‌ای و اقدام اصلاحی). NCR: باز ← Rework ← Retest ← رفع‌شده ← بسته (با الزام Retest و پربودن CAPA).

## ۱۰. امنیت

- **رمزهای عبور:** الگوریتم scrypt با نمک (salt) اختصاصی؛ رمز خام هرگز ذخیره نمی‌شود.
- **نشست‌ها:** توکن تصادفی در پایگاه‌داده به‌صورت هش‌شده ذخیره و به کلاینت فقط در کوکی `httpOnly` ارسال می‌شود.
- **محدودیت نرخ (Rate Limit):** تلاش‌های ورود ناموفق محدود و در ردیابی ممیزی ثبت می‌شوند.
- **اعتبارسنجی ورودی:** همهٔ بدنه‌ها با Zod اعتبارسنجی می‌شوند؛ کوئری‌های Prisma پارامتری هستند (مقاوم به SQL Injection).
- **کنترل خروجی:** داده‌های کاربر محدود به فیلدهای مجاز بازگردانده می‌شوند؛ کلیدها و رمزها به هیچ وجه به کلاینت ارسال نمی‌شوند.
- **ردیابی ممیزی:** جدول AuditLog فقط‌الحاقی با کاربر/نقش/عمل/مقادیر قبلی و جدید؛ پنل «مدیریت سامانه ← Audit Trail» با فیلتر نوع اقدام (گروه‌بندی‌شده)، جستجو و بازهٔ زمانی + **خروج اکسل گزارش ممیزی** برای ارائه به ممیزان.
- **تاب‌آوری رابط:** مرزهای خطای سه‌لایه (نما/صفحه/کل اپ) — خطای یک بخش هرگز کل سامانه را از کار نمی‌اندازد و با «تلاش مجدد» بازیابی می‌شود.

---

## ۱۱. پشتیبان‌گیری و بازیابی

- از پنل «مدیریت سامانه ← پشتیبان‌گیری» (فقط نقش مدیر سیستم) یک کپی زمان‌دار از پایگاه‌داده در پوشهٔ `backups` ساخته می‌شود.
- **رویهٔ بازیابی (استاندارد SQLite):** سرویس را متوقف کنید، فایل پشتیبان را جایگزین `db/custom.db` کنید و سرویس را دوباره اجرا کنید. پیش از جایگزینی، از فایل فعلی کپی بگیرید.
- در استقرار جدی، پشتیبان‌گیری خودکار زمان‌بندی‌شدهٔ خارج از میزبان (مثلاً رونوشت شبانه به محل جدا) توصیه می‌شود.

## ۱۱-ب. ورود و خروج داده‌های اکسل

مسیر: **مدیریت سامانه ← ورود/خروج اکسل** (ورود: فقط مدیر سیستم؛ خروج: نقش‌های اصلی).

**ورود داده (جادوگر سه‌مرحله‌ای):**

1. فایل Excel را رها کنید — ساختار هر شیت به‌صورت خودکار تشخیص داده می‌شود:
   - **موجودی انبار:** سرستون‌های «کد کالا / گروه کالا / نام کالا / موجودی» (ستون فعلی یا اولیه، هرکه پر باشد)
   - **BOM محصول:** «کدکالا / نام کالا / تعداد» — نام شیت یا انتخاب شما محصول را مشخص می‌کند
   - **سوابق تولید:** «تاریخ (شمسی) / شماره سریال / ورژن / سیم‌کارت / سنسور» + بلوک اختیاری «خدمات پس از فروش» (تاریخ فروش، مرکز/بیمارستان، تاریخ تحویل، تعویض قطعات)
   - **تأمین‌کنندگان:** «تامین کننده / ادرس سایت / کد / کد ایزو»
2. شیت‌های موردنظر را انتخاب و برای BOM/تولید محصول مقصد را تعیین کنید.
3. «شروع ورود» — گزارش کامل شامل ایجاد/به‌روزرسانی/رد و فهرست هشدارها (تطبیق‌های تقریبی، کدهای تکراری، اقلام ناشناخته) نمایش داده می‌شود.

**رفتار امن ورود داده:**

- رکورد تکراری (کد یا نام یا سریال) هرگز دوباره ساخته نمی‌شود؛ به‌روزرسانی می‌شود.
- تغییر موجودی همیشه با رکورد «اصلاح موجودی» در دفتر گردش کالا ثبت می‌شود.
- نسخهٔ قبلی BOM خودکار بازنشسته می‌شود (کنترل نسخه — هیچ BOM بازنویسی نمی‌شود).
- تطبیق نام اقلام چندلایه است و «توافق ارزش» را چک می‌کند: 100uf با 1000uf و 10v با 25v یکی گرفته نمی‌شوند.
- تاریخ‌های شمسی (۱۴۰۳/۰۴/۲۸) خودکار به تاریخ میلادی تبدیل می‌شوند.
- دادهٔ نمونهٔ اولیه با اسکریپت `npm run db:reset-business` (فایل `scripts/reset_business.ts`) قابل پاک‌سازی است — کاربران و نقش‌ها حفظ می‌شوند.

**خروج داده:** هفت خروجی آماده (قطعات و موجودی، تأمین‌کنندگان، دستگاه‌ها، مشتریان، BOM، دفتر گردش کالا، پشتیبان کامل چندشیتی) با سرستون فارسی، چیدمان راست‌به‌چپ، تاریخ جلالی و قالب‌بندی رنگی. چهار قالب خالی استاندارد نیز برای آماده‌سازی داده در دسترس است.

## ۱۲. رفع اشکال‌های رایج

| مشکل | راه‌حل |
|------|--------|
| خطای Prisma: `Cannot find database` یا جدول خالی | مسیر `DATABASE_URL` در `.env` را به مسیر مطلق (absolute) اصلاح کنید؛ سپس `npx prisma generate` را دوباره اجرا کنید |
| `@prisma/client did not initialize yet` | `npx prisma generate` و سپس ری‌استارت سرور توسعه |
| پورت ۳۰۰۰ اشغال است | `npx next dev -p 3001` |
| اجرای seed با خطای «tsx پیدا نشد» | `npm install -D tsx` یا `bunx tsx scripts/seed.ts` |
| بازنشانی کامل داده‌ها | فایل `db/custom.db` را حذف کنید؛ `npx prisma db push` و `npx tsx scripts/seed.ts` را اجرا کنید |
| نمایش نامناسب فونت فارسی | فونت وزیرمتن به‌صورت لوکال داخل پروژه است (`public/fonts`) و نیازی به اینترنت یا نصب فونت ندارد؛ در مرورگرهای بسیار قدیمی فونت جایگزین سیستم (Tahoma) به‌کار می‌رود |
| خطای مجوز (403) هنگام عملیاتی | طبیعی است؛ هر نقش فقط مجوزهای خود را دارد. با حساب `admin` امتحان کنید |

## ۱۴. اعتبارسنجی انجام‌شده

- **Lint:** صفر خطا (ESLint).
- **تست‌های مثبت/منفی API:** رد مجوز نقش‌ها (403)، بلاک تجهیزات کالیبراسیون منقضی، بلاک تست نهایی روی سفارش در حال تولید، بلاک شروع تولید با کمبود بحرانی، Retest زنجیره‌ای و RESOLVED شدن NCR، گاردهای آزادسازی/تحویل، مصرف اتمیک BOM (رد کامل در کسری)، رد ایجاد درخواست «دستور» بدون شمارهٔ دستور.
- **آزمون مرورگر (E2E):** ورود، داشبورد، درگ واقعی کارت روی کانبان با گذار موفق، زنجیرهٔ ۱۰ مرحله‌ای، دفتر گردش، نمای موبایل ۳۹۰px بدون سرریز، بدون خطای کنسول.
- **ممیزی نگارش فارسی:** یکدست‌سازی خودکار نیم‌فاصله‌ها در کل رابط و پیام‌های API.
